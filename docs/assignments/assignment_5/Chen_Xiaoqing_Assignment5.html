Create Time Bins

We need to aggregate trips into hourly intervals for our panel data structure.

Code 
indego <- indego %>%
  mutate(
    # Parse datetime
    start_datetime = mdy_hm(start_time),
    end_datetime = mdy_hm(end_time),
    
    # Create hourly bins
    interval60 = floor_date(start_datetime, unit = "hour"),
    
    # Extract time features
    week = week(interval60),
    month = month(interval60, label = TRUE),
    dotw = wday(interval60, label = TRUE),
    hour = hour(interval60),
    date = as.Date(interval60),
    
    # Create useful indicators
    weekend = ifelse(dotw %in% c("Sat", "Sun"), 1, 0),
    rush_hour = ifelse(hour %in% c(7, 8, 9, 16, 17, 18), 1, 0)
  )

Interpretation:

The line graph compares average hourly ridership patterns on weekdays and weekends over a 24-hour period. 1.6 Temporal Lag Features & Train/Test Split

Create Temporal Lag Variables

The key innovation for space-time prediction: past demand predicts future demand.

Why Lags?

If there were 15 bike trips from Station A at 8:00 AM, there will probably be ~15 trips at 9:00 AM. We can use this temporal persistence to improve predictions.

Code 
# Sort by station and time

Temporal Train/Test Split

CRITICAL: We must train on PAST data and test on FUTURE data!

Why Temporal Validation Matters

In real operations, at 6:00 AM on March 15, we need to predict demand for March 15-31. We have data from Jan 1 - March 14, but NOT from March 15-31 (it hasn’t happened yet!).

Wrong approach: Train on weeks 10-13, test on weeks 1-9 (predicting past from future!)

Correct approach: Train on weeks 1-9, test on weeks 10-13 (predicting future from past)

Code 
# Split by week

# Train on weeks 40-49 (Jan 1 - early Dec)
# Test on weeks 50-53 (rest of Dec)

Part 3: Feature Engineering & Model Improvement

3.1 New Features Motivated by Error Patterns

Error patterns from Part 2 suggest that the model struggles in three main situations:

  1. Major Q4 holidays.

    On days like Halloween, Thanksgiving, and Christmas, ridership patterns are very different from typical weekdays and weekends. These “holiday shocks” often show up as large residuals in the temporal error plots.

  2. Warm, dry weekend afternoons.

    The hourly error plots indicate that the model tends to under-predict demand on mild, sunny weekend afternoons. This suggests a strong non-linear “leisure riding” response to nice weather that is not fully captured by the linear temperature and precipitation terms.

  3. Peripheral stations far from Center City.

    Spatial error maps show larger errors at stations on the urban fringe compared with those in Center City. This points to an underlying spatial structure in demand that is not fully explained by the existing demographic variables.

To address these issues, I add three new features:

  • is_holiday (Temporal): an indicator for major Q4 holidays (Halloween, Thanksgiving, Christmas, New Year’s Eve) when demand deviates sharply from normal patterns.

  • weekend_good_weather (Weather × Temporal): an interaction capturing warm, dry weekend hours when leisure riding is especially high.

  • dist_center_km (Spatial): the distance of each station from Center City (City Hall), approximating how “central” or “peripheral” a station is in the urban structure.

Part 4: Critical Reflection

Overall model performance

In Part 1, the model with time-of-day, weekend, weather, and temporal lags (Model 2) was the best baseline. Adding demographics, station fixed effects, and rush-hour interactions (Models 3–5) did not meaningfully improve test-set accuracy, which suggests that most of the predictable structure in Q4 2024 demand is already captured by simple temporal patterns, weather, and short-term history.

In Part 3, I extended this baseline with three features motivated by the error analysis: a holiday indicator (is_holiday), a weekend–good-weather interaction (weekend_good_weather), and distance to Center City (dist_center_km). The extended model (Model 6) achieved a test-set MAE of about 0.416, slightly worse than the 0.401 MAE of Model 2, so the new features did not improve out-of-sample performance.

Why Model 6 did not improve MAE

Several factors may explain why Model 6 underperforms Model 2. The new variables are partly redundant with existing ones: holiday and weekend–weather effects overlap with weekend and lag terms, and distance to Center City correlates with demographic patterns considered earlier. Adding highly correlated predictors can increase variance and fit noise without adding much new information. In addition, major holidays and “perfect” weekend weather hours make up only a small share of Q4 data, so the model may be overfitting a few unusual days rather than learning general patterns.

This comparison highlights an important lesson: statistically significant coefficients in the training data do not guarantee better predictions. Feature engineering should ultimately be evaluated using test-set metrics such as MAE, not just in-sample fit.

Future directions

If I were to extend this work, I would try models that better handle count data and non-linear relationships, such as Poisson or negative-binomial regression and tree-based methods (random forests or gradient boosting). These could capture sharp drops on very cold or rainy days and complex interactions more flexibly than a linear model. I would also consider using a longer time span (multiple quarters or a full year) and richer spatial context, such as bike-lane density or land-use patterns, as well as rolling history features (e.g., 7-day moving averages). Any added complexity, however, should be justified by clear improvements in out-of-sample accuracy.
